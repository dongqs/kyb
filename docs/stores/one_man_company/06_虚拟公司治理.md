# 虚拟公司治理

## 花名册与角色

为一个小项目开一家虚拟公司，几十个员工各司其职，BOSS 对着花名册派活。

| 角色 | 能力 | 输入 | 输出 |
|------|------|------|------|
| 环境架构师 | K8s, 网络 | 项目 onboard.md | 命名空间 + Service |
| 依赖安装工 | apt, go mod, pip | 代码 + 环境 ID | 依赖就绪的容器 |
| Mock 师傅 | WireMock, 接口定义 | 外部 API 清单 | mock endpoint |
| 压测员 | k6, CK 查询 | 压测配置 | 压测报告 |
| 日志侦探 | CK SQL, 模式识别 | 时间范围 | 错误摘要 |
| BOSS | 任务拆解, 派活, 验收 | 用户需求 | 任务分配 + 迭代指令 |

每个人都有自己喜欢的书（偏好的参考文档类目），Agent 有了人格和经验偏好。

## 工作日志 + 记忆分层

三层记忆架构：

| 层级 | 存储 | 特征 | 用途 |
|------|------|------|------|
| 短期 | Context | 快速读写，用完即丢 | 当前任务指令、临时变量 |
| 中期 | ClickHouse | 可查询、可聚合、可老化 | 任务日志、指标、错误记录 |
| 长期 | Git | 不可变、可追溯、可审计 | 复盘报告、模板、花名册变更 |

每份工作写日志：agent_id、任务、动作、参考了哪本书、产出、耗时、状态。日志存入 CK，供复盘和绩效评估。

## IssueOps：发 Issue 就转起来

发一条 Issue 就十个人转起来：

1. Issue 描述需求
2. BOSS agent 解析 -> 拆解任务 -> 对照花名册点名派活
3. 多个 agent 并行执行
4. 各自写工作日志
5. BOSS 汇总关闭 Issue

## 专家验收

验收也由 AI 完成，用户不需要验收：

- **安全专家** — 检查高危端口、敏感信息泄露
- **性能专家** — 跑压测，比对基线
- **可观测性专家** — 确认日志和指标已接入 CK
- **兼容性专家** — 验证 mock 替换后业务逻辑等价

所有专家 approve → 任务完成。任何专家打回 → 退回重做。

## 开会调整流程

人类的工作就是隔段时间组织他们开会，调整流程和标准：
1. BOSS 从 CK 拉取运营数据，形成月报
2. 发 Issue 列出议题（安全规则、性能阈值、图书馆新增类目）
3. 专家异步发表意见，互相辩论
4. 所有专家同意后，人类签字
5. 执行决议 agent 更新花名册、修改验收标准、提交 Git

**分层治理模型**：
```
执行层（员工 agent）→ 验收层（专家 agent）→ 调度层（BOSS）→ 治理层（人类+专家会议）
```

最终：打通虚拟世界和手机，掌上感知 + 确认 + 语音指令。
