# OTel for MCP — Distributed Tracing Design

**Date:** 2026-05-23
**Status:** Design proposal
**Prerequisite reading:** `docs/infra/designs/mcp-observability.md` (metrics + alerts),
`docs/infra/reviews/review-mcp-D3.md` (logging).

---

## 1. Problem

The existing observability stack covers two pillars of the "three pillars" model:

| Pillar | Status | Doc |
|--------|--------|-----|
| Metrics (RED) | Defined | `mcp-observability.md` |
| Logging (structured JSON) | Defined | `review-mcp-D3.md` |
| **Tracing (OTel)** | **Missing** | **This doc** |

Without tracing, when a Claude Code MCP call fails or is slow:

- Metrics tell you **what** is slow (which tool, which server).
- Logs tell you **where** it failed (which line, which error).
- But **neither** tells you the **causal chain**: Did the transport drop the connection?
  Did the tool itself hang? Did the MCP server spend all its time deserializing a large
  input? Did the downstream (e.g., a database query called by the tool) cause the latency?

OTel distributed tracing fills this gap by modeling the **full request lifecycle** as a
tree of spans, each with start/end time, status, and attributes.

---

## 2. High-Level Trace Flow

```
┌─────────────────────────────────────────────────────────────────┐
│  Claude Code Process                                            │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  Trace: mcp.request                                        │ │
│  │  ├─ Span: mcp.transport.send      (serialize + write)      │ │
│  │  ├─ Span: mcp.transport.receive   (read + deserialize)     │ │
│  │  └─ Span: mcp.response.process    (parse result)           │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              │                                     │
│                     Context Header                                │
│                     traceparent:                                   │
│                     00-abc123...-def456...-01                     │
│                              │                                     │
│                              ▼                                     │
│  MCP Server Process                                               │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  Trace: mcp.request (continued)                             │ │
│  │  ├─ Span: mcp.server.dispatch   (routing + auth)            │ │
│  │  ├─ Span: mcp.tool.execute      (tool business logic)       │ │
│  │  │  └─ Span: mcp.tool.subcall   (downstream, e.g., SQL)     │ │
│  │  └─ Span: mcp.server.response   (serialize response)        │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

Key principle: **One trace per MCP request**, spanning Claude Code process boundary
via context propagation over the transport.

## 3. Span Model

### 3.1 Span Table

| Span Name | Parent | Kind | Where Created | What It Measures |
|-----------|--------|------|---------------|------------------|
| `mcp.request` | (root) | `CLIENT` | Claude Code, when a tool call is issued | End-to-end latency of one MCP invocation |
| `mcp.transport.send` | `mcp.request` | `CLIENT` | Claude Code transport layer | Time to serialize the JSON-RPC request + write to transport (stdio pipe or HTTP POST body) |
| `mcp.transport.receive` | `mcp.request` | `CLIENT` | Claude Code transport layer | Time to read + deserialize the JSON-RPC response |
| `mcp.server.dispatch` | `mcp.request` | `SERVER` | MCP Server, when request is received | Time to route request to handler, auth checks, param validation |
| `mcp.tool.execute` | `mcp.server.dispatch` | `SERVER` | MCP Server tool handler | Time spent in the tool's business logic |
| `mcp.tool.subcall` | `mcp.tool.execute` | `CLIENT` or `SERVER` | Inside the tool, if it calls downstream | Time for a downstream call (e.g., SQL query, HTTP fetch, file read) |
| `mcp.server.response` | `mcp.request` | `SERVER` | MCP Server, before writing response | Time to serialize the JSON-RPC response |
| `mcp.request.cancel` | `mcp.request` | `CLIENT` | Claude Code, on cancellation | Captures cancellation path separately |

### 3.2 Span Attributes (common)

All spans carry:

| Attribute | Type | Example | Source |
|-----------|------|---------|--------|
| `mcp.server` | string | `filesystem` | Server name from `.mcp.json` |
| `mcp.tool` | string | `read_file` | Tool name from capabilities |
| `mcp.request_id` | string | `mcp-req-abc123` | Generated by Claude Code |
| `mcp.session_id` | string | `sess-xyz` | Claude Code session ID |
| `mcp.transport` | string | `stdio` or `http-sse` | Transport type |
| `mcp.jsonrpc.version` | string | `2.0` | JSON-RPC version |
| `mcp.jsonrpc.method` | string | `tools/call` | JSON-RPC method name |

Span-specific attributes:

| Span | Additional Attributes |
|------|----------------------|
| `mcp.transport.send` | `mcp.params_size_bytes` (int), `mcp.transport.write_duration_ms` (int) |
| `mcp.transport.receive` | `mcp.result_size_bytes` (int), `mcp.transport.read_duration_ms` (int) |
| `mcp.server.dispatch` | `mcp.auth_result` (string: `allowed`, `denied`, `noauth`), `mcp.params_valid` (bool) |
| `mcp.tool.execute` | `mcp.tool.error` (string, if error), `mcp.tool.result_size_bytes` (int) |
| `mcp.tool.subcall` | `mcp.subcall.type` (string: `sql`, `http`, `fs`, `exec`), `mcp.subcall.target` (string) |
| `mcp.request.cancel` | `mcp.cancel.reason` (string) |

### 3.3 Status Mapping

| Span | OK Status | Error Status |
|------|-----------|-------------|
| `mcp.request` | Response received without protocol error | Timeout, transport disconnect, protocol error |
| `mcp.transport.send` | Bytes written successfully | Pipe broken, connection reset, write timeout |
| `mcp.transport.receive` | JSON-RPC response parsed | Read timeout, EOF, invalid JSON |
| `mcp.server.dispatch` | Handler found and params valid | Unknown tool, invalid params, auth reject |
| `mcp.tool.execute` | Tool returned successfully | Tool threw exception, downstream failed |
| `mcp.server.response` | Response serialized | Serialization error, OOM |

## 4. Context Propagation

### 4.1 W3C TraceContext via JSON-RPC

OTel context is propagated using the **W3C TraceContext** standard (`traceparent` header).
Since MCP uses JSON-RPC over stdio or HTTP-SSE, the propagation mechanism differs by transport:

**stdio transport:**

The Claude Code process writes JSON-RPC requests to the MCP server's stdin and reads
responses from stdout. There is no header mechanism in raw stdio. **Solution:** Inject
the `traceparent` value as an extra field in the JSON-RPC request params:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": { "path": "/tmp/x" },
    "_traceparent": "00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01"
  }
}
```

The MCP server extracts `_traceparent` from params (before dispatching to the tool),
creates a child span, and removes `_traceparent` from the arguments before passing
to the tool handler. This is transparent to the tool itself.

**HTTP-SSE transport:**

The `traceparent` header is sent as an HTTP header on each POST request:

```
POST /message HTTP/1.1
Content-Type: application/json
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call", ... }
```

This is the standard W3C TraceContext propagation and requires no JSON-RPC schema
modification.

### 4.2 Baggage

For cross-cutting concerns that are not span-specific, use W3C Baggage:

| Baggage Key | Value | Purpose |
|-------------|-------|---------|
| `mcp_session_id` | `sess-xyz` | Correlate all spans across a Claude Code session |
| `mcp_server` | `filesystem` | Propagate server name even before dispatch span is created |

For stdio transport, baggage is encoded in `_baggage` field alongside `_traceparent`:

```json
{
  "_traceparent": "00-...",
  "_baggage": "mcp_session_id=sess-xyz,mcp_server=filesystem"
}
```

### 4.3 Propagation Guarantees

| Condition | Behavior |
|-----------|----------|
| No `_traceparent` / header present | MCP server creates a **new root span** (no parent). The `mcp.request` trace will be disconnected from Claude Code's trace. This is acceptable for debugging; sampling rates should account for this. |
| Malformed `_traceparent` (invalid version, wrong length) | MCP server logs a warning, treats as no header, creates new root. |
| Trace flags `00` (not recorded) | MCP server still propagates context but may choose not to export spans (defer to head-based sampling decision). |
| Baggage overflow (>1024 bytes) | Claude Code truncates baggage to 1024 bytes. Priority: `mcp_session_id` first, then `mcp_server`. |

## 5. Implementation

### 5.1 Where to Instrument

Two components need OTel instrumentation:

**A. Claude Code (client side)**

Claude Code's MCP client module (TypeScript/JS) must:

1. Create a root span (`mcp.request`) before each `tools/call`.
2. Create `mcp.transport.send` and `mcp.transport.receive` child spans wrapping the
   transport I/O.
3. Inject `_traceparent` and `_baggage` into the JSON-RPC request.
4. Export spans via `OTLP/gRPC` or `OTLP/HTTP` to the OTel Collector.

Claude Code is an existing binary; instrumentation requires either:
- A **fork/patch** of Claude Code's MCP client (not recommended — maintenance burden).
- A **wrapper/proxy** that intercepts MCP communication (recommended — see 5.2).

**B. MCP Server (server side)**

Each MCP server (Python, Node, Go, or Ruby) must:

1. Extract `_traceparent` from params (or `traceparent` from HTTP headers).
2. Create a child span (`mcp.server.dispatch`).
3. Create `mcp.tool.execute` as a child of dispatch.
4. Optionally create `mcp.tool.subcall` spans for downstream calls.
5. Annotate all spans with attributes from section 3.2.
6. Export via OTLP.

Recommend adding OTel SDK as a dependency to each MCP server image. For Python MCP
servers, `opentelemetry-distro` + `opentelemetry-instrumentation` provides auto-instrumentation
for HTTP/gRPC subcalls with minimal code changes.

### 5.2 Recommended Architecture: MCP Proxy Sidecar

Rather than patching Claude Code or each MCP server individually, deploy a **transparent
MCP proxy** that sits between Claude Code and the MCP server:

```
┌──────────┐    stdio/SSE     ┌────────────┐    stdio/SSE     ┌────────────┐
│ Claude   │ ──────────────►  │ MCP Proxy  │ ──────────────►  │ MCP Server │
│ Code     │ ◄──────────────  │ (OTel)     │ ◄──────────────  │ Container  │
└──────────┘                  └────────────┘                  └────────────┘
```

The proxy:
1. Intercepts every JSON-RPC request/response.
2. Creates and manages all spans on behalf of both sides.
3. Injects/extracts `_traceparent`.
4. Exports spans via OTLP to the OTel Collector.
5. Requires **zero changes** to Claude Code or MCP server code.

This is the **preferred approach** because:
- No fork of Claude Code needed.
- Single point of instrumentation — works for all MCP servers regardless of language.
- Can be deployed per-server or as a shared gateway.
- Can add transport-level metrics and logging at the same point.

### 5.3 OTel Collector Pipeline

```
MCP Proxy (OTLP)
  │
  ▼
OTel Collector
  ├─ BatchProcessor (100ms, 512 items)
  ├─ Sampling (head: probabilistic, tail: latency/error-based)
  ├─ Attributes Processor (add environment, cluster, container_id)
  └─ Exporters
       ├─ ClickHouse (via OTel ClickHouse exporter)
       │   └─ Table: otel_spans (or infra.otel_spans)
       ├─ Prometheus (metrics derived from spans — RED metrics)
       └─ Jaeger/Tempo (optional, for UI)
```

**Sampling strategy:**

| Sample Type | Rate | Condition |
|-------------|------|-----------|
| Head (probabilistic) | 10% | All traces |
| Tail (latency-based) | 100% | P99 latency > 5s |
| Tail (error-based) | 100% | Any span with error status |
| Head (session-based) | 100% | Specific debug sessions (opt-in via env var) |

### 5.4 Minimal Instrumentation Example (MCP Server in Python)

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

tracer = trace.get_tracer(__name__)
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
trace.set_tracer_provider(provider)

def handle_tools_call(params):
    # Extract traceparent
    tp = params.pop("_traceparent", None)
    if tp:
        ctx = propagate.extract({"traceparent": tp})
    else:
        ctx = trace.get_current_span().get_span_context()

    with tracer.start_as_current_span("mcp.server.dispatch", context=ctx) as dispatch:
        dispatch.set_attribute("mcp.server", server_name)
        dispatch.set_attribute("mcp.tool", params["name"])

        with tracer.start_as_current_span("mcp.tool.execute") as execute:
            execute.set_attribute("mcp.tool.result_size_bytes", ...)
            result = call_tool_handler(params)
            return result
```

### 5.5 MCP Proxy Minimal Implementation (Concept)

The proxy is a simple process that:

1. Listens on stdio (or an HTTP port for SSE).
2. For each incoming JSON-RPC request:
   a. Starts `mcp.request` span (root).
   b. Starts `mcp.transport.send` span, forwards request to upstream MCP server.
   c. Ends `mcp.transport.send` span.
   d. Starts `mcp.transport.receive` span, reads response from upstream.
   e. Ends `mcp.transport.receive` span.
   f. Injects `_traceparent` into request to upstream (if server also instrumented).
   g. Returns response to Claude Code.
   h. Ends `mcp.request` span.
3. Exports spans via OTLP.

Implementation can be in any language with OTel SDK support (Go, Rust, Python, Node).

## 6. Integration with Existing Metrics and Logs

### 6.1 Trace → Metric Correlation

Every span carries `mcp.request_id` and `mcp.server` attributes, matching the metric
labels defined in `mcp-observability.md`. This enables:

- **Metrics to traces**: Given a slow metric (`mcp_request_duration_ms` P99 spike),
  query traces by `mcp.server` + time range to find the slowest request IDs.
- **Traces to logs**: Given a trace with error span, query `mcp_logs` by `request_id`
  to get structured logs from the same request.

### 6.2 Unified `request_id`

All three pillars use the same `request_id`:

| Pillar | Where `request_id` Appears |
|--------|---------------------------|
| Metrics | Label on `mcp_requests_total`, `mcp_request_duration_ms` |
| Logs | Field in JSON log event (see D3) |
| Traces | Attribute on every span |

This is the linchpin of the observability stack — any metric spike or log error can
be drilled into a trace, and any trace can be cross-referenced with logs.

### 6.3 ClickHouse Schema for Spans

```sql
CREATE TABLE infra.otel_spans (
  timestamp DateTime64(9),
  trace_id String,
  span_id String,
  parent_span_id String,
  trace_state String,
  span_name String,
  span_kind LowCardinality(String),
  service_name String,
  resource_attributes String,   -- JSON
  scope_name String,
  span_attributes String,       -- JSON
  duration_ns Int64,
  status_code LowCardinality(String),  -- OK / ERROR / UNSET
  status_message String
) ENGINE = MergeTree()
ORDER BY (service_name, timestamp);
```

This is a generic OTel span table (not MCP-specific) so all traces from all services
land in the same table. MCP-specific queries filter by `service_name = 'mcp-proxy'`
or `service_name = 'mcp-server-<name>'`.

## 7. Operational Concerns

### 7.1 Overhead

| Concern | Mitigation |
|---------|-----------|
| Span creation per request | ~5 spans per MCP call. At 1000 req/s, ~5000 spans/s. Batch export (100ms window) keeps CPU under 1%. |
| Context header injection | String field in JSON-RPC. Negligible size (<100 bytes). |
| OTLP export network | Separate from request path; async export with retry. Failure to export does not block the request. |
| Sampling | 10% head sampling by default. Latency/error-based tail sampling ensures slow/failed calls are always captured. |

### 7.2 Security

- `_traceparent` and `_baggage` are metadata only — they carry no credentials or
  sensitive data.
- If the MCP server runs in a different trust domain, the proxy can strip/regenerate
  context headers to prevent trace ID leaking internal topology.
- OTLP export should use mTLS when the collector is on a different network segment.

### 7.3 Debug Session Opt-In

For targeted debugging, set an environment variable on Claude Code:

```bash
OTEL_MCP_DEBUG_SESSION=true kyb enter my-sandbox
```

This sets head sampling to 100% for the session and adds extra attributes:
- `mcp.debug_session: true`
- Full JSON-RPC request/response bodies in span attributes (normally omitted to
  avoid high-cardinality attributes).

## 9. Summary

| Aspect | Design Decision |
|--------|----------------|
| Span model | 7 spans per MCP call, covering transport, dispatch, execution, and subcalls |
| Context propagation | W3C TraceContext via `_traceparent` in JSON-RPC params (stdio) or HTTP headers (SSE) |
| Sampling | 10% head + 100% tail for error/latency |
| Deployment | MCP proxy sidecar preferred over per-server instrumentation |
| Correlation | Shared `request_id` across metrics, logs, and traces |
| Storage | Generic `otel_spans` table in ClickHouse |

The three pillars are now fully defined:

```
Metrics: mcp_observability.md  (counters + histograms + alerts)
Logs:    review-mcp-D3.md      (structured JSON → ClickHouse)
Traces:  THIS DOC              (OTel spans → OTel Collector → ClickHouse)
```

These three documents together form a complete observability story for Claude Code MCP.
