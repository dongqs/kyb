# 100 个 Agent 自动迭代的编译瓶颈

## 起源：100 个 Agent 同时迭代

项目启动时，我们开了 100 个 Agent，让它们自动迭代代码。每个 Agent 独立生成、修改、编译代码，形成一个多智能体自动进化系统。

Agent 之间协作方式多样：有的生成新功能，有的修复 bug，有的重构已有代码。理论上，Agent 越多，迭代速度越快——但现实很快给了我们当头一棒。

## 瓶颈浮现：编译卡住了整个流程

100 个 Agent 同时启动后，代码生成速度飞快，调度也顺畅。但很快我们发现，**编译成为了瓶颈**。

每个 Agent 生成代码后，需要编译验证。如果串行编译，每个编译几秒到几十秒，100 个就是几分钟甚至十几分钟。Agent 在排队等待编译结果时完全空闲，整个迭代循环被拖慢。

更糟糕的是，Agent 生成的代码往往相似度很高——同一个基础架构上的不同改动。但因为没有共享编译缓存，每个 Agent 都在重复编译大量相同的内容，浪费了宝贵的 CPU 资源。

## 第一轮优化：增量和缓存

### 增量编译

最直接的思路：只编译被修改的部分。设计上让 Agent 尽量只改动单个文件或模块，而不是触发全量构建。构建系统从 Make 切换到 Ninja（比 Make 快 30% 以上），利用模块化设计实现精确增量编译。

### 编译缓存：ccache / sccache

Agent 生成的代码虽然各有不同，但底层的头文件、公共库是相同的。引入 ccache（C/C++）和 sccache（分布式缓存）后，重复编译内容直接从缓存命中，速度提升显著。

关键教训：不能让 100 个 Agent 各自写本地缓存——每个 Agent 的独立环境意味着缓存无法共享。必须使用共享缓存（NFS 或 Redis 后端），让所有 Agent 的编译结果汇聚到一个缓存池。

### 并行编译与资源管控

`-j$(nproc)` 不够，改为 `-j$(nproc)*1.5`，但要监控内存防止 OOM。如果磁盘 I/O 是瓶颈，把源码和对象文件移到 tmpfs（内存文件系统），彻底消除磁盘等待。

## 第二轮优化：链接器成为新瓶颈

编译速度上来了，链接器又成了短板。对于 C/C++ 项目，链接阶段往往是单线程的，ld（GNU ld）在处理大量对象文件时速度极慢。

解决方案：换用 mold 或 lld。

- **mold**: 现代高速链接器，比 GNU ld 快 5-10 倍，是当前最快的选择
- **lld**: LLVM 生态的链接器，速度也远快于 ld

对于 Rust 项目：启用 `lld` + `incremental = true`。
对于 Go 项目：虽然 Go 编译本身已经很快，但也可以调整 `-ldflags` 等参数优化。

换用 mold 后，链接时间从几十秒降到了秒级。这是投入产出比最高的优化之一。

## 第三轮优化：异步编译队列

即使单次编译很快，100 个 Agent 同时提交编译请求，仍然会造成资源争抢。

解决方案：**异步编译队列**。

- 限制并发编译任务数为 CPU 核心数
- Agent 提交代码后，编译任务进入队列排队执行
- Agent 不阻塞等待，而是订阅编译结果回调
- 编译不再是线性等待，整体吞吐量最大化

这套机制类似于生产者-消费者模型：Agent 是生产者，编译队列是消费者。只要编译速度跟得上 Agent 的生成速度，系统就能稳定运行。

## 第四轮优化：语法级预筛选

很多 Agent 生成的代码存在语法错误，不值得进入完整的编译流程。在触发真正编译前，先用快速语法检查过滤掉明显错误的输出：

- C/C++: `clang -fsyntax-only` / `gcc -fsyntax-only`
- Go: `go vet`
- Rust: `cargo check`（比完整编译快一个数量级）

这类检查比完整编译快 10 倍以上，能在早期快速淘汰无效输出，减轻编译队列压力。

## 第五轮：架构级反思——CI/CD 才是终极答案

做了以上所有优化后，我们停下来反思了一个更根本的问题：

**为什么每个 Agent 迭代都必须立即可运行？**

答案是不需要。

Agent 生成代码后，不需要立即编译。可以把生成和编译解耦成两个阶段：

1. Agent 生成候选代码，提交到版本库
2. CI/CD 流水线批量编译所有提交
3. 编译结果与 Agent 迭代记录关联
4. 根据结果选优、进化

这就是真正的分布式编译——不是本地堆机器，而是让 CI/CD 成为编译中枢。

每轮迭代流程变成了：

```
Day 1: 100 个 Agent 生成候选代码 → 提交 MR
Day 2: CI 自动拉取所有分支，批量编译+测试
Day 3: 根据 CI 结果选优，反馈给 Agent 进化
```

虽然单次延迟增加了（从秒级到天级），但整体吞吐量反而更高。编译不再阻塞 Agent 的生成过程，Agent 可以不断生成、提交、继续生成。

更重要的是，这套机制解开了 Agent 对本地编译环境的依赖。Agent 可以在任意环境中生成代码，编译统一由 CI 基础设施承载。分布式编译集群（distcc、icecream）甚至云上弹性编译都可以在此基础上自然接入。

## 幸福的烦恼

回顾整个过程，有一个感悟值得记下来：

> **编译瓶颈是幸福的烦恼——说明前面调度和生成已经不是问题了。**

当你发现瓶颈在编译时，意味着你已经解决了更困难的问题：
- 100 个 Agent 的调度和协同没有问题
- Agent 的代码生成质量足够高，值得进入编译
- Agent 之间没有陷入死循环或无效迭代

编译是一个"好"的瓶颈——它是一个工程问题，有明确的解法和优化路径。调度问题、收敛问题、质量问题才是更难缠的。

## 总结

| 优化层次 | 方案 | 效果 |
|---------|------|------|
| 构建系统 | 增量编译、Ninja、模块化 | 减少 60-80% 的重复编译 |
| 编译缓存 | ccache / sccache 共享缓存 | 缓存命中率 > 50% |
| 链接器 | mold / lld 替代 ld | 链接提速 5-10 倍 |
| 资源管理 | tmpfs、并行度调优 | 消除 I/O 瓶颈 |
| 队列 | 异步编译队列 | 吞吐量最大化 |
| 预筛选 | 语法级快速检查 | 减少 90% 无效编译 |
| 架构 | CI/CD 解耦编译和生成 | 终极方案，不再阻塞 |

最终，编译不再是瓶颈。但幸福的烦恼也意味着：该担心下一层瓶颈了——测试、部署、评估……优化永无止境。
