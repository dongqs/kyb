# OODA 循环与 5 分钟巡检

## 从指挥官到系统架构师

最开始，我是那个站在中央调度台前的人。每看到一个信号，就要亲自做出反应。Agent 卡住了？我去看。CI 黄了？我去查。构建日志里有异常？我一行一行地读。Buildkite 挂了？我来重启。

这叫指挥，不叫管理。这叫瓶颈。

问题是：当一切都要经过我，一切就都停在我这里。而我的注意力只有那么宽，带宽只有那么大。Agent 跑得再快，也要等我。等我读完日志，等我做出判断，等我发出指令。死亡螺旋就是这样来的——我累了，慢了，出错了，然后整个系统跟着崩溃。

## 五分钟的觉醒

解决方案很简单：不要让 boss 做决策，让系统做决策。

于是有了那个 5 分钟的 cron。每五分钟一次循环，雷打不动。Observe——看 Agent 们在哪里，在做什么，有没有卡住。Orient——判断当前状态是正常还是异常，是等着还是需要干预。Decide——这个 Agent 需要重启吗？那个任务需要重新分配吗？有东西死掉了吗？Act——执行决策，发出调整指令。

五分钟。不是五秒，不是五十分钟。五秒太短，什么都看不出来；五十分钟太久，黄花菜都凉了。五分钟是一个心跳。足够让系统知道你还在，但不会让你成为瓶颈。

## 系统的操作系统

这个 cron 不是一个技术工具。它是这个团队的操作系统。

以前是我在指挥。我站在中间，所有人看着我。现在是一个系统在运转。我做的事不再是指挥交通，而是搭好交通灯，修好路面，然后在交通灯搞不定的时候站出来。

这是一个微妙的转变。指挥官的视角是：**我来处理每一个异常。** 架构师的视角是：**我让系统有能力自己处理异常，我只处理系统搞不定的异常。**

cron 就是那个兜底。不是取代人，而是确保没有东西被遗忘。Agent 可能会忘，但 cron 不会。Agent 可能会卡住，但 cron 会把它捞起来。Agent 可能会死，但 cron 会发现它死了，然后决定怎么办。

## 循环本身才是答案

OODA 循环的精髓从来不是某个环节做得有多好。Observe 做得再完美，如果 Orient 是错的，也没用。Decide 做得再快，如果 Act 没执行，等于零。

精粹在于**循环本身**。

五分钟跑一圈。这一圈观察到的信息，影响下一圈的判断。上一圈的行动结果，变成这一圈的观察对象。每一圈都在修正前一圈的误差。每一圈都在缩小现实与目标之间的距离。圈数越多，系统越稳。

这就是为什么不能等。不能等一个 Agent 回复了再继续 —— 你不回，我下次再问。不能等一个构建完成了再做下一步 —— 你的构建和我下一次巡检不冲突。**没有什么事是必须要等的。** 等，就是停。停，就是死。

## 12 个 Agent，一个循环

那天下午，12 个 Agent 同时在跑。有人写代码，有人开 MR，有人盯 CI，有人迁移数据库。而我没有崩溃。不是因为我能同时处理 12 件事，而是因为我不需要同时处理 12 件事。

我需要做的只是：每五分钟看一眼仪表盘，做几个二元决策，推动循环继续。

Agent 们不需要我。它们需要的是那个循环。

## 做 boss 这件事，我是摔出来的

说实话，学做 boss 这件事，我是真的摔了很多次才学会的。

不是谦虚，是真的花了一整天，从早摔到晚。十几次吧——看到一段代码就想改，看到 build 日志就想读，遇到决策就想问"你觉得呢"而不是直接拍板。每次反应过来，发现自己又在做 worker 的事。

有一刻我记得很清楚。Agent 发来一条消息说 CI 黄的。我盯着那条消息，手悬在键盘上，脑子里已经在想"我去看看"。然后我突然意识到：这不是我的工作。我派一个人去看。我派一个人去修。我派一个人回来汇报。我不需要离开这个座位。

那个瞬间，系统开始运作了。不是我更聪明了，是我终于 stop getting in the way。

## 模式会固定，但需要练习

到晚上收工的时候，模式已经固定了。5 分钟的 cron 在跑。Agent 们各司其职。死亡螺旋没有出现。不是我变厉害了，是系统变强了。

但我不骗自己：明天肯定还会摔。又会忍不住去看代码，又会忍不住去读日志，又会忍不住去当一个 worker。

只是明天会摔得少一点，爬起来快一点。这就是进步。

## 核心教义

OODA 循环不是项目管理方法论，不是生产力技巧。它是一种**存在方式**：

- 不要让信息停在你这里 > 让它流动
- 不要让决策等着你 > 让循环替你做
- 不要试图处理一切 > 让系统处理常规，你处理例外
- 不要停 > 每五分钟转一圈

当你发现自己在等人、在等日志、在等构建、在等审批——停下来问自己：**我是不是又变成瓶颈了？**

如果答案是"是"，那就去把瓶颈变成循环。
