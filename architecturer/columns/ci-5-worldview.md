# 专栏：五路大军围剿一个 CI bug

**关联章节：** [第二章](02-growing-pains.md)

---

master CI 红了一整天。不知道原因。日志翻了几遍，没有明显线索。

常规做法：派一个人去查。给他说"你去看看 CI 怎么红的"，等他回来说"原因可能是 XXX"。

我的做法：**不派一个。派五个。五个不同角度的 agent 同时进攻。**

## 五路大军

| Agent | 角度 | 假设 |
|-------|------|------|
| 第一性原理 | 从零推起 | 所有上层理解都是错的 |
| 网络 | 网络/代理问题 | 容器连不上外网 |
| 环境 | Docker/CI 差异 | 本地能跑 CI 不能跑 |
| Git | 合并/历史问题 | merge 冲突或 bad commit |
| 日志 | 答案就在日志里 | 只是还没看懂 |

第一性原理那个最先到终点。

## 它发现了什么

根因是 `Kyb.in_container?` 这个方法。它在 CI 环境里返回了 `true`——因为它检测到 `/proc/1/cgroup` 有 Docker 的痕迹——然后触发了 kill 进程的逻辑。测试跑着跑着就被自己杀了。

修复极其简单：加上更严格的判断条件，让方法知道"我是在测试环境里，不是在真正的 kyb 容器里"。

## 为什么五路比一路强

如果我只派一个 agent，它会从某个角度开始查。如果方向错了，半小时后发现不对，换个方向再来。串行试错。

五个同时试，不管哪个方向是对的，总有人先到。时间 = 最长路径 ÷ 并行度。这是基础数学。

而且最妙的是：**五个 agent 读同一个 log，看到了五个不同的东西。** 日志 agent 看到的 grep 结果和环境 agent 看到的完全不一样。因为他们带着不同的预期在看。

这件事之后，我再也没用单个 agent 查过复杂故障。
