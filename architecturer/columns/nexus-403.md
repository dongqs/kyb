# 专栏：Nexus 403 追击记

**关联章节：** [第一章](01-first-contact.md)

---

`readonlyuser` 在 Nexus 上拉某些依赖时返回 403。这个问题阻塞了好几个项目。

常规做法：一个 agent 慢慢查日志、试密码、看配置。

我的做法：**三个 agent 同时用不同策略试。**

## 三路并行

1. **凭据轮换 agent** — 试不同的用户名和密码组合
2. **URL 重构 agent** — 试不同的 URL 路径和仓库名
3. **版本替换 agent** — 看看是不是版本不存在

版本替换那个先回来了。它发现我们请求的依赖版本在 Nexus 的快照仓库里确实不存在。换了存在的版本之后，7 个模块全部编译通过。

## 意外的收获

三路并行的同时，我们也画出了 Nexus 的权限边界：

| groupId | readonlyuser 能访问？ |
|---------|---------------------|
| com.leyantech.base | ✅ 能 |
| com.leyantech.leyan | ❌ 403 |
| com.leyantech.chaos | ❌ 403 |

这不是凭据问题，是 groupId 级的权限隔离。`readonlyuser` 本来就不被允许访问某些 group。

两个问题混在一起了：
1. 有些 groupId 是真的 403（权限不够）
2. 有些是 404（还没发布到那个仓库）
3. 有些时候 VPN 能解决（网络层面的间歇问题）

知道边界在哪，比解决边界问题更重要。因为我们知道了哪些项目可以直连 Maven Central 绕过去，哪些需要申请权限。

## 这个案例说明什么

三个 agent 同时试不同方案，一个成功了就行。如果我一个一个试，还在第一个尝试上打转。

**并行不只是为了快——是为了提高命中率。** 而且在过程中你得到的副产品（权限边界地图），比最初想解决的问题更有价值。
