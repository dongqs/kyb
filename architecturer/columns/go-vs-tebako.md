# 专栏：为什么不做 Go 重写

**关联章节：** [第四章](04-the-overhaul.md)

---

有人建议我用 Go 重写 kyb。"更现代"、"性能更好"、"静态编译"。

我认真做了评估。

## Go 重写方案

工作量：13-16 天。
结果：功能零增长。
代价：双代码库维护，新 bug 风险。

## Tebako 方案

Tebako 把 Ruby（含 stdlib）编译成一个单文件二进制。不需要改任何代码。几天就能搞定。

## 对比

| 维度 | Go 重写 | Tebako |
|------|---------|--------|
| 工期 | 13-16 天 | 几天 |
| 功能增量 | 零 | 零 |
| 维护成本 | 双代码库 forever | 不变 |
| 风险 | 重写引入新 bug | 低 |
| 收益 | 心理满足感 | 单文件部署 |

Go 重写的唯一收益是心理上的——"用了一个更现代的语言"。技术和业务上没有任何增量。

不干。

## 更深一层的思考

Ruby 对 kyb 来说其实是一个特别好的选择：

- **Zero deps 不是偶然的。** kyb 只用 Ruby stdlib。没有任何 gem 依赖。这不是 Ruby 的功劳，是刻意控制的结果。
- **Expressiveness 是资产。** Agent Runtime 的核心逻辑是字符串处理、进程管理、容器编排——Ruby 在这些场景下表达力比 Go 强。
- **Tebako 解决了部署问题。** 之前担心的 "Ruby 项目部署麻烦" 被 Tebako 解决了。编译出来就是一个二进制。

有些重写是为了还技术债。有些重写只是为了证明"我能用那个语言写"。我不做第二种。
