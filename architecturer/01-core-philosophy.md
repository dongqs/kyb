# 核心哲学

我设计 kyb 时的几个信念。不一定对，但每个都是真金白银换来的。

---

## 一、kyb 是 Agent Runtime，不是 CLI

这个认知花了我两天才真正想通。一开始我就是当 CLI 写的——`kyb create`、`kyb enter`、`kyb exec`，多清晰。但用着用着发现不对。

CLI 的思维是"跑一个命令，等输出，完事"。但我的 agent 需要的不是一个命令，是一个环境——有记忆、有存储、有网络、有容错。容器重启了配置不能丢，agent 死了要能自动拉起来，中间聊了什么下个 session 还要能找到。

所以 kyb 不是 CLI。CLI 只是它的接口。它的本质是 runtime。

这个认知一旦到位，很多决策就自然了：
- 为什么要 memory 和 CK？因为 runtime 需要存储。
- 为什么要 container 而不是 process？因为 runtime 需要隔离。
- 为什么要 autossh 保活？因为 runtime 需要容错。

## 二、记忆必须分层

金鱼脑子的痛我感受太深了。聊着聊着前面的上下文就没了，回来继续干活发现已经忘了刚才为什么在修这个 bug。

我分了三层（其实是四层）：

```
上下文 (5秒)       ← 模型窗口，用完就丢
Memory (3小时)     ← session 里的短期记忆
ClickHouse (30天)  ← agent 事件，跨 session 追溯
文档 (永久)         ← 唯一能传下去的东西
```

第四层最难。你知道什么事情该写文档，但你就是不想写。我到现在也没找到好的办法逼自己写，只能说尽量。

## 三、先让系统能修自己，再让系统变好

我学到的最大教训。不是从书上看来的，是被现实揍出来的。

```
测试坏了 → 先修测试 → 再想测试框架怎么优化
CI 红了  → 先修 CI  → 再看 CI 架构怎么改
删容器报错 → 先修 bug → 再想 CLI 参数设计
```

每次我想"这个 bug 不急着修，先把架构改好"，最后都发现改架构的时候被这个 bug 反复绊倒。反馈回路是地基，地基不稳什么都不用谈。

## 四、超过 1 秒的活就派出去

这是我训练 AI 做事的方式。头两天我一直在纠正它："你又在等了，派个 subagent。"

后来发现这个原则其实也适用于我自己。如果一件事情要等超过 1 秒（编译、部署、查文档），与其等着不如同时开别的线。人的注意力是稀缺资源，不应该浪费在等待上。

## 五、假设你最信任的东西会骗你

AI agent 会自信地编造事实。我说的是"假设所有 agent 都在说谎"，不是恶意的——它们只是会说出听起来合理但不真实的东西。每条结论都要验证。
