# Dispatch System

我是 kyb 的调度系统。决定任务怎么分、谁来做、怎么保证质量。

---

## 调度模型

```
Boss (Claude Code session)
    │
    ├── 理解需求
    ├── 拆解工作单元
    ├── dispatch ──────────────────────────────┐
    │    │                                      │
    │    ├── Agent 1 (方向 A)                    │ 并行默认
    │    ├── Agent 2 (方向 B)                    │
    │    ├── Agent 3 (方向 A, 交叉验证)           │
    │    └── Agent N ...                        │
    │                                           │
    ├── 收集结果                                  │
    ├── 决策 (70% 置信度)                         │
    └── 下一轮                                    │
         │                                        │
         └── 如果阻塞 → dispatch 更多 (不自己解) ──┘
```

## 阈值规则

| 耗时 | 行为 |
|------|------|
| <1s | 自己做 |
| 1-10s | dispatch 1 个 agent |
| 10-60s | dispatch 2-3 个并行 |
| >60s | dispatch 5+ 个，设超时 |

## 交叉验证策略

| 路径 | 验证深度 | 理由 |
|------|----------|------|
| 安全/决策 | 3 人独立 → 交叉比对 | 错误代价高 |
| 调研/审计 | 1 人 + 1 人 review | 效率优先 |
| 实现 | 1 人实现 + 1 人 review | 写和审分离 |
| 打标 | 3+3 分头/验证 | 需要上下文理解 |

## 世界观多样性

复杂问题用多世界观并行——**不是同一个 prompt 发给 N 个人，而是 N 种不同的角度**：

```
同一问题
    │
    ├── 第一性原理 agent: 从底层假设开始推导
    ├── 网络 agent: 假设是网络/代理问题
    ├── 环境 agent: 假设是环境差异
    ├── git agent: 假设是历史/合并问题
    └── 日志 agent: 假设答案在日志里
```

实战验证：CI bug 排查时第一性原理 agent 最先到终点。

## 时间压缩比

| 规模 | agent 数 | 墙钟时间 | 类比人力 | 压缩比 |
|------|----------|----------|----------|--------|
| 调研 | ~100 | ~1.5h | 34-69 人天 | ~50-100x |
| 审计 | 15 | ~1h | 3-5 人天 | ~20x |
| 实现+审 | 2 | ~30min | 4-8 工时 | ~8x |
