# 调度系统

我是怎么派活的。这是我花时间最多的地方——不是写代码，是训练 AI 学会怎么派活。

---

## 核心原则

**超过 1 秒的活就派出去。**

听起来简单。我纠正了 AI 至少二十次它才真的记住。每次它自己在等编译结果、等测试跑完、等我回复——我就说：派个人去做。

## 调度模型

```
我（人类架构师）
  │  给需求、看结果、做决策
  ▼
Boss (Claude Code session)
  │  拆任务、派 agent、收结果
  ├── Agent 1 (方向 A)
  ├── Agent 2 (方向 B)
  ├── Agent 3 (交叉验证方向 A)
  └── Agent 4 ... (并行默认)
```

Boss 不自己做实现。Boss 做决策。

## 我怎么决定派多少人

| 场景 | 派法 |
|------|------|
| 简单问题（<1s）| 自己看 |
| 中等（1-10s）| 1 个 agent |
| 复杂（10-60s）| 2-3 个并行，不同方向 |
| 疑难（>60s）| 5+ 个，不同 worldview |
| 大规模调研 | 几十个，分方向 × 交叉 |

## 交叉验证策略

安全相关的、决策性的：至少 3 人独立做，再交叉比。
调研类的：1 人做 + 1 人 review。
打标分类的：3 人分头 + 3 人验证。

为什么这么分？因为 3 人交叉在非关键路径上是浪费。80% 的情况结论一致，多花 2 倍 token 不值得。

## 我学到的

**世界观多样性比数量重要。** 同一个问题给 5 个不同角度的 agent（第一性原理、网络、环境、git、日志），比给 10 个同样 prompt 的 agent 有用得多。这不是理论——CI 挂了一整天的时候第一性原理那个 5 分钟找到了根因。

**时间压缩是真实的。** 138 份调研文档一夜出完，我自己写至少要几周。成本 $35-70，质量达到初稿水平。ROI 是量级上的正。

**但不可盲目扩。** 100 个 agent 同时跑 boss 盯不过来，输出格式不统一汇总也痛苦。我现在倾向 20-30 一批，而不是一波推。
