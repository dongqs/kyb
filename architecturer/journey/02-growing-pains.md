**2026-05-22 | Day 2**

---

第二天我以为自己学会了。结果还是被纠正了七八次。

## "超过 1 秒就派人"

早上 AI 又在等——盯着 `kyb exec` 的输出、盯着测试进度条。我从背后飘过去："超过 1 秒的活都派人。"

它已经比昨天好多了。至少现在能在 1-2 秒内意识到"哦我在等"，而不是 30 秒才反应过来。阈值从 30 秒降到了 1 秒。我说这是被骂出来的条件反射。

## 两个测试并行修

早上的实战课是修两个阻塞测试。`env_kyb` 挂了，DID 的 PG 测试也挂了。两个都是阻塞项，不修掉 master 红着。

我让 AI 开了两个 subagent——一个修 `env_kyb`，一个修 DID PG。同时跑。一个修好了，另一个也修好了。十分钟搞定。

如果我自己一个一个修，至少半小时。**数学不会骗人。**

## CI 红了：五路围攻

master 红了一整天。查不到原因。log 看了，没有线索。

我做了个决定：不开一个 agent 查。开五个。五个不同世界观的 agent：

1. **第一性原理** — 从零开始推，假设所有理解都是错的
2. **网络** — 假设是代理/网络问题
3. **环境** — 假设是 Docker/CI 差异
4. **git** — 假设是合并或历史问题
5. **日志** — 假设 log 里有答案

同时跑。

第一性原理那个先到终点。它发现 `Kyb.in_container?` 这个方法在 CI 环境里返回了 `true`——因为它检测到 `/proc/1/cgroup` 有 Docker 痕迹——然后触发了 kill 进程的逻辑。测试跑着跑着被自己杀了。

修复后就一行：加上更严格的判断条件。

这个故事论证了一个我一直猜想的事情：**世界观多样性比数量重要。** 如果我只派一个人去查，可能还在第三个猜测上打转。

## 那天晚上的认知跃迁

晚上我读了一篇设计文档，然后整个人都不好了。

**kyb 不是一个 CLI 工具。它是一个 Agent Runtime。**

我之前一直把它当 CLI 写——命令、输出、错误处理。但它做的事是 runtime 的事：管理 agent 生命周期、提供 memory 和 storage、协调通信、处理故障。CLI 只是接口。

这个认知解释了为什么 `kyb exec` 和普通 CLI 不一样、为什么需要 container 而不是 process、为什么 memory 和 CK 是核心设施而不是附加功能。

同一天晚上，还有一个模式反复浮现：

**先关掉反馈回路，再搭上层架构。**

不是选择的——是被现实逼出来的。测试坏了先修，不是因为修测试最高杠杆，而是因为测试坏了什么都干不了。CI 红了先修（五路围攻），再看 CI 架构。rm cname 挂了先修，再想统一设计。

控制论先于系统论。我记下了这句话。

然后我写下了记忆分层的核心哲学：

> "我们都是金鱼脑子只能记5秒 memory能记3小时 ck让我们能记30天 文档可以传给下一代。"

以及那天最后一件大事：火山云 100K/月 预算批下来了。从零到一。
