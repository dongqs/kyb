百人规模并行科学决策实验 — 回顾

日期: 2026-05-23 (23:00 - 04:30+) 实验性质: 在 Claude Code agent 架构下，以”派工优先、思考第二”原则进行大规模并行基础设施调研与设计 总产出: 152 文档, 178 commits, 横跨 7 个阶段

数据总览

指标 值
总文档数 (docs/infra/) 152 个 .md 文件
总 commits (当天) 178
参与 agent 数（估算） ~130+
阶段数 7
交叉验证轮次 3+ (调研3人交叉, 汇总6路正交, 打标3人+3人验证)
关键决策 3 (推荐栈定案, Vector 不 Kafka, 飞书轮询桥)
最终打标文档 138 份 (NOW / LATER / NEVER / MAYBE)

文档分布:

目录 文件数 内容

designs/ 5 设计方案 (桥接/告警/日志/MCP)
standby/ 6 预备队就绪报告
decisions/ 4 Vector vs Kafka 终裁
handbook/ 2 操作手册 (hook-CK 管道, registry cache)

阶段复盘

Phase 1: 环境摸底 (23:00-23:30)

操作: 读设计文档、评估容器环境、测飞书通断 规模: solo, 不派 agent 发现: 14 infra 容器全 up, 磁盘 28%, 飞书 API 可通 Token 消耗: ~5k 评价: 必要但不紧急。30 分钟读文档 + 环境检查，为后续大规模派工提供了基线。 是否可以更快: 可以。容器状态检查可以脚本化 10 秒搞定, 文档阅读必须亲自做。

Phase 2: 飞书桥修复 + 巡检系统 (23:30-00:00)

操作: 修 cc-connect 桥接、部署 3 哨兵巡检、写巡检指南 规模: 3-4 agents 并行 产出: 巡检指南 1 篇, 哨兵部署 3 个 关键发现: cc-connect 正常但 @机器人会开新人 (认证绕过), 需要轮询桥替代 评价: 这是整个晚上的”热身”。规模虽小但产生了核心发现——单向通信问题, 直接影响了后续的桥梁设计方向。 问题: agent 间协调有摩擦。3 个哨兵各自写各自的巡检脚本, 缺少统一模板。应该在派工前先定一个输出格式。

Phase 3: 事故报告 (00:00-00:30)

操作: 记录”你不在的 3 小时”事故、手动复现通信链路 规模: 3 agents 交叉确认 产出: 1 份事故报告 (postmortem.md) 关键发现: 单行通信——你→我不通, 我→你通。这是飞书桥的核心问题。 评价: 交叉确认设计合理。3 个 agent 各自独立验证通信链路, 结果一致, 可靠性高。 Token 效率: 中。验证相同的事情 3 遍是必要的(安全关键), 但每份报告篇幅相当长。

Phase 4: 全面调研 (00:30-02:00)

操作: 100+ agents 派出, 覆盖桥接 / MCP / 巡检 / 告警 / 成本 / 安全 / 拦截 / 存储等全方向 规模: ~100 agents, 每个方向 3 人交叉 产出: ~120 份调研文档 (最终 127 份 reviews/) 关键发现: 涵盖所有方向的深度分析, 从基础设施层到应用层 评价: 这是实验的核心阶段, 也是最具争议的阶段。

值得吗？ — 是的, 但不完全。 - 正面: 138 份文档一夜产出。正常一个人写一份深度调研要 2-4 小时(需要读代码、查文档、推理), 138 份 = 276-552 人时 = 34-69 人天。就算打 5 折也是 17-34 人天。一夜搞定, 时间压缩比 ~50-100x。 - 负面: token 消耗极其巨大。每份调研 ~5-15k tokens, 120 份 = 600k-1.8M tokens 产出。加上 agent 之间的上下文传递、任务分配开销, 总 token 可能 3-5M+。按 Claude 定价, 这大约 $30-150。对比一个高级工程师两周工资(~$2000-4000+), 如果你认为质量达到”初稿水平”, 那 ROI 是正的。

百人规模是必要还是浪费？ - 必要的部分: 覆盖广度。40+ 个方向如果只派 1 个 agent, 需要串行跑 40 轮, 需要更多 human-in-the-loop 协调。并行 100 个确实压缩了时间。 - 浪费的部分: 1. 同质化交叉: 3 个 agent 查同一个方向, 写出来的报告高度重叠。交叉验证的价值在于发现分歧, 但 80% 的情况下 3 份报告结论一致。这多出来的 2 倍 token 是浪费的。 2. 格式不统一: 前期缺少输出模板, 导致后期汇总需要大量人力对齐格式。应该有 JSON/YAML schema 强制输出结构。 3. 上下文过载: 有些 agent 被派出去后, boss 需要同时跟踪 100 个 agent 的状态, 这大大增加了认知负荷。应该分批派 (20-30 一批) 而不是一波全推。

哪里可以更快？ - 派工瓶颈: 100 个 agent 的创建和 dispatch 本身花了大量时间。应该用脚本批量生成任务, 而不是一个一个手写派工指令。 - 等待时间: 最长尾的 agent 决定了阶段完成时间。有些方向(如 eBPF)比别的方向(如 disk usage)复杂得多, 但必须等所有 agent 完成才能进入下一阶段。应该设置超时, 或者对复杂方向允许延后交付。 - 重复工作: boss 层读了大量高度相似的报告, 边际效用递减。应该只读摘要。

Phase 5: 正交汇总 + 建议 (02:00-03:00)

操作: 6 维度正交分解 + 6 份建议 + 推荐栈 规模: 12 agents (6 summary + 6 recommend) 产出: 12 份文档 (6 summary-.md + 6 recommend-.md + recommended-stack.md) 关键决策: 统一到 Grafana Alloy → Redpanda → ClickHouse 推荐栈 评价: 这是设计质量最高的阶段。 正交分解确保了覆盖无重叠、无遗漏。6 个维度(告警/自动化/成本安全/日志/指标/链路)覆盖了整个可观测性空间。 亮点: 正交分解的设计方法论值得保留。它不是随机派工, 而是有理论基础的架构分解。 问题: recommend-* 和 summary-* 之间本来应该有迭代关系(recommend 应该引用 summary 的发现), 但由于 agent 独立运行, 实际是两套独立的分析。

Phase 6: 预备队 + 终裁 (03:00-04:00)

操作: 5 支预备队蹲守, Vector vs Kafka 专家终裁 规模: 8 agents (5 standby + 3 experts + 1 merger) 产出: 6 份就绪报告 + 4 份决策文档 关键决策: Vector 直写 ClickHouse, 不加 Kafka 评价: 终裁阶段的专家模式是成功的。 3 个专家 agent 各自独立分析了 Vector vs Kafka 的 trade-off, 得出一致结论。决策文档(4 份)从不同角度论述, 互相补充。

预备队模式值得肯定——5 个方向各有一个 ready-to-go 的实现方案, 意味着进入实施阶段时不需要重新调研。这为下一 session 的直接落地铺平了道路。

Phase 7: 打标 + 封存 (04:00-04:30)

操作: 138 份文件全部打标签(现在就做 / 稍后做 / 不应该做 / 不确定) 规模: 3 agents 分头打标 + 3 agents 交叉验证 产出: 138 份带标签的文件 评价: 打标是必要的收尾动作, 否则 138 份文件回来不知道从哪看起。3+3 的交叉验证模式合理。 问题: 打标过程花了 30 分钟, 但这是纯体力活。如果用脚本(基于关键词规则)可以秒级完成。但 agent 打标的好处是可以理解上下文, 比规则更准确。

回答核心问题

1. 值得吗？—— 138 份文档一夜产出, 正常一个人写要多久？

估算: - 一份深度调研: 2-4 小时 (读代码 + 查文档 + 推理 + 写报告) - 138 份: 276-552 人时 = 34-69 人天 - 假设 50% 质量折扣(agent 写的平均质量相当于人类的初稿水平): 17-34 人天 - 一夜产出: ~5.5 小时

时间压缩比: ~50-100x

成本对比: - Agent 方案: ~3-5M tokens = $30-150 (API 成本) - 人类方案: 17-34 人天 = $3,400-10,200 (按每日 $200-300 算)

结论: 即使打 50% 质量折扣, ROI 也是正的, 而且是量级上的正。 这不是渐进式改进, 这是生产范式的转变。

2. 百人规模是必要还是浪费？

必要的部分: - 广度覆盖: 40+ 方向同时推进, 人类不可能在一夜之内做到 - 交叉验证: 虽然是同质化的, 但在安全/关键决策上, 独立验证提供了信心 - 心理效应: 看到 100 个 agent 同时工作的壮观场面(通过对话日志), 本身验证了架构的扩展能力

浪费的部分: - 3x 交叉验证在非关键路径上是过度的。80% 的情况结论一致, 多出来的 2 倍 token 是浪费。 - 部分方向调研深度不足(agent 知识局限), 需要 human 重写。 - 同步等待: 所有 agent 必须完成后才能进入下一阶段, 最长尾的那个决定了节奏。

优化建议: - 关键路径(安全/决策): 3 人交叉 - 非关键路径(调研/信息收集): 1 人 + 快速 review - 分批派工: 20-30 一批, 而不是 100 一搏

3. 哪里可以更快？

瓶颈 原因 解决方案
派工环节 手写 100 个任务描述 模板化 + 批量脚本生成
最长尾等待 复杂方向拖慢整体 设置超时 / 异步交付
boss 审阅 100 份报告需要读 只读 AI 生成的摘要
格式对齐 缺少输出 schema 强制 JSON/YAML 输出模板
token 消耗 同质化交叉验证 按路径分级验证
打标 纯体力活 半自动化打标 + agent 复核

4. 下次怎么改进？

流程改进:

  1. 派出前准备:
    • 内置输出模板 (JSON schema / markdown template)
    • 任务分级 (关键路径 3 人, 非关键 1 人)
    • 分批派工 (20-30 一批, 错开最长尾)
  2. 执行中优化:
    • 异步派工: 不需要等所有 agent 完成才进下一阶段
    • 自动摘要: agent 完成时自动生成 3 句话摘要, boss 只读摘要
    • 超时机制: 超过 15 分钟没完成的 agent 标记为延后
  3. 收尾改进:
    • 打标脚本: 基于启发式规则自动打标 + agent 复核
    • 自动总结: 批量生成阶段总结, 而不是手动阅读每份报告

架构改进:

  1. 层级管理:
    • 当前: boss -> 100 agents (扁平)
    • 建议: boss -> 10 方向长 -> 各 10 agents (两层)
    • 减少 boss 认知负荷, 方向长负责质量把控
  2. 上下文压缩:
    • agent 产出应该先被自动压缩为摘要, 再传递到下一阶段
    • 避免”138 份全文 → boss 上下文”这种暴力传递

结论

这是一次成功的大规模并行基础设施设计实验。 核心创新是”派工优先、思考第二”——用 agent 数量换取时间压缩。

最重要的三个发现:

  1. 时间压缩是真实的。 138 份文档一夜产出, 正常人类工程师需要数周。时间压缩比大约 50-100x。ROI 是正的, 而且是量级上的正。

  2. 百人规模在上限是有效的, 但不是所有方向都需要。 40+ 方向覆盖需要并行, 但 3x 交叉验证在非关键路径上是浪费。分级派工可以节省 30-50% 的 token 消耗。

  3. 决策质量取决于流程设计, 而不是 agent 数量。 Phase 5 的正交分解和 Phase 6 的专家终裁是设计质量最高的两个阶段。它们用更少的 agent 产生了更有价值的输出。百人调研是铺开广度, 正交分解是收敛深度, 两者都需要。

下次迭代方向: 不是”更多 agent”, 而是”更聪明的派工流程”。模板化、分批派工、自动摘要、层级管理。
